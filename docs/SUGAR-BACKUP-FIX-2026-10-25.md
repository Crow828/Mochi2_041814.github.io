# 血糖日记备份修复与卡顿报告核对

## 已确认的数据问题

用户提供的恢复备份中仍有 3 条饮食记录、2 天预估糖化。记录保存在 default 联系人命名空间，页面按全局命名空间读取，因而显示为空。根因是联系人旧数据迁移的排除清单漏掉 sugar-diary 与 sugar-hba1c，并非这份 JSON 完全没有备份血糖日记。

修复将两类记录列为全局个人数据；读取旧版本 default 副本时，仅在全局键不存在且数据已初始化后恢复，不删除旧副本，不覆盖现存全局记录。现存空数组或空对象视为有效状态，防止已删除记录重新出现。完整备份的覆盖清单明确列出饮食与糖化记录，优先描述当前全局数据。

## 恢复和安装

解压 mochi2-fix，将内部内容复制到仓库根目录，合并文件夹、替换同名文件，然后提交推送。等待验证通过，更新网站后进入日历的血糖日记。旧位置仍有数据时会自动读取恢复；无需再次导入旧整库备份，避免覆盖后来新增记录。若旧副本之外还有缺失日期，需要包含那些日期的其他备份才能进一步恢复，不能从本文件编造记录。

包内包含上次聊天滚动、标识层级和验证修复；保留 v4.2.6 刷新弹窗修复标签，以构建时间区分。README 保持用户原文，不进入替换包。用户数据文件和诊断报告均不打进代码包。

## 验证范围

实际导出完整 JSON 文件，检查两类数据，再实际通过导入入口恢复与重开；旧位置恢复、正常全局数据、多次重开、现有空状态均已覆盖，Chrome 与 WebKit 均通过。

真实恢复备份在隔离浏览器中恢复后，找回 3 条饮食记录和 2 天糖化；937 条原有聊天、989 张专属字卡和 4 张公用字卡仍能读取，原有外观字号检查通过。没有操作用户手机或线上存储。

## 卡顿自检报告

报告记录了 59 次前台冻结，最长帧间隔约 3.9 秒；44 次点按中位响应约 7 ms，最慢约 1.94 秒，最慢点按在字卡库，最慢帧现场也涉及字卡库和设置。说明除了聊天滑动，还有页面首次进入和任务处理的停顿。

ka-tick 标记距离冻结起点的中位间隔约 2 秒，不能据此确认保活是原因；desk-layer-warm 同样只是较远的前序标记。fish-tick 在现代码中属于自动日常检查计时器标签，并不直接证明某个游戏造成卡顿。脚本显示的 116 次回收属于应用累计推测，不能当作 iOS 官方进程回收次数。

同一份备份在隔离浏览器、Chrome CPU 4 倍减速下复查，字卡管理首次进入到后续帧约 0.46–0.59 秒，后续进入约 0.08–0.14 秒；点击处理本身约 5–17 ms。首次内容构建有额外开销，但没有复现真机报告的 3–4 秒冻结，不能用此测试断言问题已完全修复。后续应在同一设备同一路径对照采样；保活开关不作自动更改，不以清空聊天或字卡处理卡顿。
